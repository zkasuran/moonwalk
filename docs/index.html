The lifecycle

Sign → check → settle.

One endpoint offers both rails. The 402 carries the x402 requirements in PAYMENT-REQUIRED and the channel offer in X-CHANNEL-REQUIRED. The caller picks by which header it sends back.

01 · SIGN

A voucher, not a transaction

The payer funds the channel once with a signed EIP-3009 authorization, then signs one EIP-712 voucher per call. A voucher is a cumulative total for one person, so the newest one supersedes every earlier one and a lost voucher costs nothing.

02 · CHECK

Against the contract, not a config

Before the work happens the service checks the signature, the cumulative and that person's SpendGuard cap. It reads the cap from the contract, so refusing a call and failing to redeem it can never disagree.

03 · SETTLE

One transaction, every call

Once enough has accrued the service calls redeem with the newest voucher per person. One transaction, one USDC transfer, every call since the last redeem. The payer's own tx count stays 0.

Cheap enough to meter. Bounded per person.

to settle one $0.001 call

Thirty calls redeemed in one transaction cost $0.006565 in gas. On the per-call rail the same call costs $0.001873 to settle, which is nearly twice the price of the thing being bought. The payer's transaction count over the whole run: 0.

1 wallet, N caps

each person capped in the contract

A subject is keccak256("discord:<guildId>:<userId>"), so SpendGuard holds a limit per person while the agent spends from one wallet. A voucher over someone's cap cannot be redeemed by anyone, the operator included. In the proof run one was refused with CapExceeded.

Lineage

MoonWalk grew out of NanoPay. The Discord agent and the per-call x402 rail were built for the Lepton Agents Hackathon (Canteen × Circle). NanoPay is still the agent surface and the live bot. New for the Encode × Circle Programmable Money Hackathon: the three contracts, the payment channel with cumulative vouchers, the on-chain per-person caps, the ServiceRegistry, the dual-rail 402 with its /channel endpoints plus the proof run above. The rails are the new work.

For the judges

Every question, answered.

The honest version, up front.

Is the money real?

Yes. Real testnet USDC moves between two distinct wallets on Arc, status 1 on every receipt. You can click each hash on this page. They are permanent on-chain records that need no server to verify. In the channel run the payer's balance went from 9.788000 to 9.758000 USDC, exactly the $0.03 that was metered.

Why a payment channel and not just x402 per call?

Because the fee beats the price. One x402 settlement of a $0.001 call cost $0.001873 in gas on Arc, measured on the receipts above. The channel spreads that cost: 30 calls redeemed in one transaction cost $0.006565 in total, which is $0.000219 a call. x402 is still the right rail for a first call or a one-off, so the same endpoint offers both.

Is the payer really gasless?

On the happy path yes, measured rather than claimed: the payer's transaction count was 0 before and 0 after a run that opened a channel, metered 30 calls, settled them and closed. It signs the deposit, every voucher and the close. Anyone can submit those. In production the service does. One exception: if the service goes dark the payer has to send requestClose and withdraw itself, which needs USDC for gas.

Is the agent really deciding or is it scripted?

It is a real model tool-use call over a priced catalog. It can buy a tool, pick a different tool or answer for free and spend nothing. Ask it a greeting and it spends $0; ask for a live price and it buys one. The budget is enforced in code after the model picks, so a hallucinated number can never overspend.

Why does the agent show 0 on-chain transactions if it paid?

EIP-3009, the x402 "exact" scheme. The agent signs a transfer authorization off-chain; a facilitator broadcasts it and pays the gas. On every receipt the from is the facilitator, not the agent. The to is the USDC contract. The payer needs USDC, nothing else.

What is genuinely yours versus the Circle SDK?

The three contracts are ours: the channel, the cap enforcement and the registry, with 51 tests behind them. So is the Python chain package with its committed ABIs, the service-side rail that quotes and batches, the payer-side voucher client, the dual-rail 402 and the Discord surface. Circle's parts are USDC with EIP-3009 on Arc plus the x402 protocol plumbing. The settlement layer on top is the build.

What stops one person draining the agent's wallet?

SpendGuard, in the contract. Each person is a hashed subject with its own limit, lifetime or per window. A voucher that would push them past it makes redeem revert. The operator cannot override that at redeem time. It also fails closed: a guarded channel with no cap configured cannot spend anything at all. When the bot sees a cap is reached it refuses the call rather than quietly switching to the other rail.

Which Circle tools does it use?

The x402 exact scheme, EIP-3009 USDC on Arc, an embedded facilitator that settles in-process plus USDC-as-gas. The two-wallet split (agent payer, service facilitator) is what makes each settlement a real transfer between distinct parties, not a wallet paying itself. The channel adds EIP-712 vouchers and EIP-3009 receiveWithAuthorization for the deposit.

Has anyone actually used it?

The bot has been live and paying in Discord since early July. The settlement rows on this page are pulled from the payment store rather than typed in. Rows marked as Discord are real people in a server paying sub-cent USDC on Arc. The channel rail is new, so its evidence is the full lifecycle run above rather than months of traffic. We report the real number, never an inflated one.

What are the limits you are not hiding?

Testnet only, because Arc has no mainnet. The challenge window on this deploy is one hour, so a service offline for an hour loses whatever it had not redeemed. The service trusts nothing but it does have to keep its vouchers: lose that store and it loses the right to collect. The Discord marketplace writes to the ServiceRegistry, and the service wallet submits those transactions because a member has no wallet or gas, so a listing records the operator as its lister while payTo is the member's own address. The contracts are unaudited. The full list is in the README.
